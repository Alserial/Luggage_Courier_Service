# 项目审查报告

审查日期：2026-07-17  
审查范围：小程序前端、CloudBase 云函数、订单状态机、审核、匹配、证据和项目文档  
审查结论：当前适合交互原型和受控演示准备，不适合真实用户试点。

## 总体判断

项目已经具备较完整的 MVP 结构：需求发布、行程发布、匹配、报价、订单、Mock 支付、交接、证据、争议和审核页面均已有雏形，产品边界文案也基本遵守低风险、低价值、非物流和非资金托管原则。

但真实交易闭环尚未建立。当前最重要的问题不是页面数量，而是云端失败时仍显示成功、关键状态更新不具备原子性、状态权限过宽、证据没有真实文件链路，以及未核验行程仍可进入成交流程。

## P0：上线或试点前必须修复

### 1. 云服务失败会被伪装成成功

`miniprogram/services/cloud.ts` 在异常时直接返回调用方传入的 fallback。发布、报价、接受报价、支付、交接、证据和争议页面中，多处 fallback 是 `ok: true`。

影响：断网、云函数未部署或权限错误时，用户仍会看到“提交成功”，但数据库可能没有任何记录，破坏订单和审计可信度。

建议：生产模式禁止成功型 fallback；只允许明确的 demo 模式使用演示数据。失败时统一返回错误状态，并提供重试入口。

### 2. 真实订单支付页使用固定 Demo 金额

`miniprogram/pages/payment/index.ts` 没有读取真实订单，显示金额和提交金额都来自 `demoOrder`。

影响：真实报价金额不是 Demo 金额时，后端会返回金额不匹配；即使金额碰巧一致，页面显示的订单信息也不可信。

建议：支付页先调用 `order-get` 获取订单和服务费总额；服务端应以订单记录为准校验金额，前端不应决定最终支付金额。

### 3. 普通参与方可以直接处置争议订单

`cloudfunctions/order-transition/index.js` 允许任一订单参与方将 `disputed` 转为 `refunded`、`completed` 或 `cancelled`。

影响：争议结果可被当事一方直接改变，不符合管理员审核和审计要求。

建议：将争议裁决拆成管理员/审核员专用云函数；普通参与方只能提交争议和补充证据。退款只处理服务费记录。

### 4. 关键写入没有事务和幂等

接受报价、Mock 支付、交接和发起争议都包含多次独立数据库写入。例如先创建订单，再更新报价，再写审计日志。

影响：重复点击、并发请求或中途失败可能生成重复订单、重复支付记录，或出现业务数据已变但审计日志缺失的半完成状态。

建议：为关键流程增加事务或条件更新；强制 `operationId`/provider transaction id 幂等；接受报价时同时锁定报价并防止重复订单。

### 5. 证据尚未接入真实文件存储

前端只选择本地临时文件，提交时发送 `fileCount`，没有上传 CloudBase Storage，也没有传递真实 `fileIds`。

影响：证据记录无法查看、下载、关联或用于争议裁决。

建议：先上传到 CloudBase Storage，再将不可变的 `fileId` 写入 `evidence`；后端验证文件归属、证据类型、订单参与关系，并保持 append-only。

### 6. 未核验行程仍可报价和成交

`trip-create` 会把新行程设为 `active`，即使 `verificationStatus` 为 `pending` 或 `manual_review`；`offer-create` 只检查行程是否 active，没有检查核验状态。

影响：没有航班或行程凭证的携带人仍可进入订单流程，与“订单确认前必须完成行程核验”的规则不一致。

建议：匹配和报价至少要求 `verificationStatus === approved`；如果需要允许提前曝光，应区分“可展示”和“可成交”状态。

### 7. 订单交接后没有完整履约操作入口

前端目前只暴露支付、交接、证据和争议操作，没有调用 `order-transition` 将订单推进到 `in_transit`、`arrived`、`delivered` 和 `completed`。

影响：真实订单无法在小程序内完成生命周期闭环。

建议：按订单角色和当前状态提供下一步操作，并将所需证据作为状态转换前置条件。

## P1：下一阶段补齐

- 需求表单缺少物品照片、尺寸、购买方式等字段。
- 行程表单缺少国家、机场/车站、不可接受品类和交接偏好等字段。
- 匹配算法中的信用、地点和价格兼容目前是固定值；没有剩余容量预占，可能出现超额匹配。
- 审核员打开需求或行程详情时，详情读取函数只允许创建者读取，可能回退到 Demo 数据而不是显示真实审核对象。
- CloudBase 集合、索引、权限和存储目录没有可重复执行的初始化脚本，主要依赖手工配置。
- 云函数依赖统一使用 `wx-server-sdk@latest`，部署不可复现，建议固定版本并维护锁文件。
- TDesign 已安装但未实际使用；多数列表页缺少完整的加载、错误、空状态和重试反馈。
- 缺少管理员争议裁决、服务费退款 Mock、评价、站内消息和状态通知。

## 验证结果

通过：

- `npm run check:files`
- `npm run typecheck`

但当前没有云函数单元测试或集成测试；`check:files` 仅检查文件存在，不能证明权限、状态机、并发和数据一致性正确。

## 建议开发顺序

### 第一阶段：真实数据与交易完整性

1. 移除生产环境成功型 Demo fallback，增加明确的 `DEMO_MODE`。
2. 修复支付页，读取真实订单并由服务端计算/校验金额。
3. 为接受报价、支付、交接、争议和状态流转增加事务、条件更新和幂等。
4. 限制普通用户的状态转换权限，增加管理员争议裁决和服务费退款 Mock。
5. 接入 CloudBase Storage，保存真实文件 ID 并校验证据归属。
6. 增加交接后的在途、到达、送达和完成操作。

### 第二阶段：测试与运营基础设施

1. 增加状态机、权限、重复请求、金额校验和匹配过滤测试。
2. 增加测试用户、审核员、需求、行程、报价和订单的 seed 脚本。
3. 固定云函数依赖版本，补齐 CloudBase 集合、索引和权限初始化。
4. 运行一条真实数据 happy path 和一条风险 path，再考虑受控试点。

## 试点前验收标准

- 断网或云函数异常不会显示成功。
- 同一报价重复点击只能生成一个订单。
- 未核验行程不能成交。
- 普通参与方不能裁决争议或直接退款。
- 证据记录包含真实可访问的 `fileIds`。
- 一笔真实订单可以从 `pending_payment` 完整走到 `completed`。
- 每次状态变化都有对应审计日志和必要证据。
